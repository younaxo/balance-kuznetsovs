# Архитектурные решения

Короткий журнал ключевых технических решений и почему они были приняты.
Не описывает весь проект — только развилки, где был реальный выбор.

## Стек

**Next.js 16 (App Router, Turbopack) + React 19 + TypeScript strict.**
Next даёт Server Components (меньше JS на клиенте), Server Actions
(мутации без ручных API routes там, где это уместно), встроенную
оптимизацию изображений/шрифтов и единый деплой-артефакт. Turbopack —
дефолт в Next 16, отдельно включать не нужно.

**Tailwind CSS v4** — CSS-first конфигурация (`@theme` в globals.css),
без `tailwind.config.js`. Design-токены (цвета, радиусы, шрифты) заданы
как CSS custom properties, что упрощает light/dark тему без дублирования
классов.

**Drizzle ORM, не Prisma.** Оба варианта были в базовом списке ТЗ.
Выбран Drizzle:
- SQL-first API — миграции читаются как обычный SQL, легче ревьюить;
- нет отдельного query-engine бинарника и codegen-шага при каждом
  изменении схемы (Prisma Client генерируется отдельно);
- меньше рантайм-зависимостей, что соответствует требованию
  "минимизировать количество зависимостей";
- `drizzle-kit generate` не требует живого подключения к БД для
  генерации миграций, только для их применения — удобнее для CI.

**PostgreSQL** — реляционная модель (заявки, атрибуция, аналитика,
отзывы, сессии) с внешними ключами и уникальными ограничениями подходит
лучше, чем документная БД; требование ТЗ также прямо называет Postgres.

**Аутентификация — собственные server-side сессии, не NextAuth/Lucia.**
Схема: opaque-токен в HttpOnly cookie, в БД хранится только его
SHA-256-хеш (компрометация БД не даёт увести активные сессии); пароли —
Argon2id (`@node-rs/argon2`, победитель Password Hashing Competition,
рекомендован OWASP). Своя реализация — потому что admin-аутентификация
здесь простая (email+пароль, без OAuth/соцвходов), и полноценный
auth-фреймворк был бы избыточен ради этого объёма функциональности;
архитектура (`admin_users`/`admin_sessions`) готова для добавления 2FA
без изменения схемы.

**Motion (бывший Framer Motion)** — для scroll-reveal и микроанимаций.
`MotionConfig reducedMotion="user"` уважает `prefers-reduced-motion`
для transform-анимаций на уровне библиотеки; глобальный CSS-фолбэк в
`globals.css` дополнительно гасит обычные CSS-transition/animation.

**Radix UI (Dialog/Label/Select-примитивы) + tw-animate-css.**
Диалоги, фокус-трап, ARIA-атрибуты, блокировка скролла body и
Escape-обработка в модалках — вручную переписывать эту логику
корректно и доступно намного рискованнее, чем взять проверенный
примитив. `tw-animate-css` — CSS-only набор анимационных утилит под
Tailwind v4 (замена устаревшего `tailwindcss-animate`, у которого нет
v4-плагина), используется вместе с `data-state` атрибутами Radix.

## Public/Admin разделение layout

Изначально Header/Footer/диалоги заявки-квиза/cookie-баннер были в
корневом `app/layout.tsx` — из-за этого они утекали и в `/admin/*`,
что для панели управления не нужно и визуально неверно (обнаружено на
этапе визуального QA). Исправлено через route group:
`app/(public)/layout.tsx` — публичный сайт (header/footer/диалоги/
аналитика), `app/admin/(protected)/layout.tsx` — защищённая часть
админки (guard + `AdminShell`), `app/admin/login` — вне защищённой
группы. Корневой `app/layout.tsx` остался только с шрифтами и темой
(общее для обеих веток).

## Server/client разделение переменных окружения

`src/lib/env.ts` изначально валидировал и серверные, и клиентские
переменные в одном файле. Один клиентский компонент импортировал из
него `clientEnv` — и весь модуль (включая валидацию `DATABASE_URL`/
`SESSION_SECRET`) попадал в клиентский бандл и падал в браузере, где
этих переменных нет. Исправлено разделением на `env.server.ts`
(с `import "server-only"`, компилятор ловит случайный импорт из
клиента на этапе сборки) и `env.client.ts` (только `NEXT_PUBLIC_*`).

## Аналитика: собственная first-party система

Требование ТЗ — не писать `fetch('/analytics')` в каждом компоненте.
Архитектура: `trackEvent()`/`TrackedLink`/`TrackedButton` на клиенте →
единый Route Handler `/api/analytics/event` → `recordAnalyticsEvent()`
на сервере, который решает, писать ли событие в БД, на основании
cookie согласия (`bk_consent`). first-touch/last-touch атрибуция —
через отдельные короткоживущие cookie (`bk_ft`/`bk_lt`), не через
localStorage (согласуется с SSR и не требует лишнего JS на первый
рендер).

Яндекс.Метрика была подключена опционально (через
`NEXT_PUBLIC_YANDEX_METRICA_ID`), но по просьбе клиента полностью
удалена из проекта (2026-09-01) — счётчик не нужен, first-party
аналитики достаточно. Если понадобится в будущем — переменная и
компонент `YandexMetrica` восстанавливаются из истории git, остальной
код (CSP, cookie-баннер) не завязан на неё жёстко.

## Кэширование/статика

Изначально публичные страницы рендерились статически (`○` в выводе
`next build`), а обновления из админки применялись через
`revalidatePath()`. Это работало локально (реальный Postgres доступен
на этапе `next build`), но **ломало Docker-сборку**: внутри
изолированного build-контейнера живой БД нет и не должно быть, а
`next build` пытался подключиться к ней для статической генерации
`/`, `/contacts`, `/services` и т.д. — сборка падала с `ECONNREFUSED`
(обнаружено при реальной проверке `docker build`, не предположительно).

Исправлено: `export const dynamic = "force-dynamic"` в
`app/(public)/layout.tsx` — вся публичная часть сайта рендерится
динамически на каждый запрос. Это одновременно решает проблему сборки
и снимает необходимость вручную дергать `revalidatePath()` при каждой
admin-мутации (хотя эти вызовы оставлены — на динамических маршрутах
они безвредный no-op, а не мусор, если модель когда-нибудь вернётся к
частичной статике). Cache Components (`cacheComponents`) в Next 16
не включались, чтобы не усложнять модель кэширования сверх
необходимого для этого масштаба проекта.

## Rate limiting

In-memory sliding-window (`src/server/security/rate-limit.ts`) для
заявок/квиза/аналитики, плюс отдельная БД-таблица `login_attempts` для
блокировки brute-force входа в админку (переживает рестарт процесса,
в отличие от in-memory). Redis сознательно не добавлен — при текущем
однонодовом Docker/VPS-развёртывании (см. README) in-memory лимитер
достаточен; при переходе на несколько инстансов интерфейс
`checkRateLimit()` можно заменить на Redis-реализацию без изменений
на вызывающей стороне.

## Отзывы Avito

Легальное исследование (см. README, раздел Avito) показало, что
публичная страница профиля закрыта antibot-firewall (QRATOR, ответ
HTTP 429 с CAPTCHA) — автоматический парсинг не реализован, так как
это требовало бы обхода антибот-защиты, что прямо запрещено ТЗ.
Вместо этого — `ReviewProvider` абстракция (`AvitoReviewProvider`
честно возвращает пустой результат с объяснением,
`ManualReviewProvider` для ручного ввода через админку) и честный
empty state на публичном сайте, пока отзывов нет.
